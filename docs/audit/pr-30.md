## 3. Manual review of the diff

- No ROM routine address, no offset inside the ROM, no instruction listing in comments or docs.
- Data: the bit patterns and guard pixels of `tests/rectpens.s` / `tests/menufont.s` are authored test vectors; no
  font, string or image from the ROM.
- `public-repo.md` check on `git diff 21ed998 pr-30` and `git diff 630a450 pr-30`: no hit; commit message clean.
- Provenance stated in the PR description and in `docs/audit/dpaint-pens.md`: public structures, the existing
  behaviour specs and DPaint III running on our ROM; the reference-ROM comparison stayed in an isolated audit.
- Code: RectFill (directly and through its wrap path) now takes the eight per-plane minterms stored in the RastPort
  (`dr_rect_rp`); the pen-derived path (`dr_rect`) stays for the other callers. Every internal caller that writes the
  pens or the draw mode directly before a RectFill (`gad_ghost`, `mn_ghost`, the solid BltBitMap fill on its private
  RastPort) refreshes the minterms first (`gfx_minterms`) and the two ghost routines restore the client's minterms
  afterwards; ClearEOL/ClearScreen switch pen A through SetAPen. A grep of the PR tree for direct pen/draw-mode writes
  finds no other RectFill caller left with stale minterms. InitRastPort already initialises the minterms. Side note:
  ClearEOL/ClearScreen now also reset the line-pattern phase (SetAPen), which only matters to a client mixing a
  patterned Draw with a text clear.
- Contributor's records: their figures agree with ours. Differences: (1) the binary record applied the fixed
  thresholds without the `tiers` corpus; with the full controls the derived threshold is the same, 40 / 19 / 19;
  (2) its token counts differ slightly from ours (fixed build ID `audit-dpaint-pens`); (3) "no passage intersects a
  changed line" holds for the default `--limit 20` AROS report only; the full list has the short idiom passages
  above, below the baselines.
