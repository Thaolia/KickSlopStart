## 3. Manual review of the diff

- Sources: the gauge clamps used to total and halves both until total fits 15 bits before the 16-bit `mulu`/`divu`;
  AddDosNode, with dos present, starts the handler through `bcpl_starthandler` when ADNF_STARTPROC is set, the node
  has no task and the caller is a process, then always enqueues the BootNode. No ROM address, no instruction listing
  in comments, no data table, no "taken from the ROM" wording.
- Analysis pages (`uae-hd-boot-v34.md` §4.1-§4.4, §9, `handlers-v34.md`, `workbench-task-v34.md`): behaviour,
  structure offsets and packet fields only; no ROM address or instruction listing found (checked with the usual
  patterns and by reading). One sentence reports what a code reading established ("the chain-walk loop only tests
  `ln_Succ`, `bn_DeviceNode` and `dn_Next`"): a description of which fields are read, acceptable as behaviour.
- Correctness remarks for the contributor (not clean-room issues):
  1. the ADNF_STARTPROC start does not take `DOS_HSEM` nor re-read `dn_Task` under it, unlike `dos_resolve` and
     `dos_startmounts`: a process resolving the device at the same moment could start a second instance;
  2. the name passed to `bcpl_starthandler` is the device name without ':' (`dos_startmounts` passes "DH0:"); harmless
     for the ROM file system, and the page says 1.3 does not pass a usable name there;
  3. the code relies on the DeviceNode's BSTR name being NUL-terminated (true for UAE and MakeDosNode nodes).
- The page states that 1.3 starts an ADNF_STARTPROC handler on first access, while the PR text says from the Initial
  CLI; the analysis track's probe of 2026-11-10 (`rom-filesystem-v34.md` §1.4) saw a partition's handler started during
  the Initial CLI's set-up, which `dos_startmounts` reproduces.
